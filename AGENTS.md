# AGENTS.md

This file provides guidance to AI coding agents (Claude Code and others that support the AGENTS.md convention) when working with code in this repository.

## Commands

- `flutter pub get` — install dependencies after editing `pubspec.yaml`.
- `dart analyze` — type-check and lint the whole project. Run this after any change; it is the primary correctness check in this repo (no CI configured yet).
- `dart run build_runner build --delete-conflicting-outputs` — regenerate `*.g.dart` Hive adapters. **Required any time a `@HiveType`-annotated class (anything in `lib/features/*/data/models/`) is added or edited.**
- `flutter test` — run widget/unit tests.
- `flutter run` — run the app on a connected device/emulator.

## Architecture

This is a Flutter score tracker for the card game **Flip 7**. The codebase follows a **clean architecture, feature-first** layout under `lib/features/<feature>/`, each split into `domain/`, `data/`, and `presentation/`. Three features exist: `game` (the score tracker itself), `calculator` (a mode-dependent card calculator used to compute a round's score), and `settings` (game settings + app theming).

### `game` feature layers

- **`domain/`** — pure Dart, no Flutter/Hive imports. Contains:
  - `entities/`: `Game`, `Player`, `Round`, `PlayerRound`, `GameMode` (enum), `PlayerSortMode` (enum: `listOrder` / `byScore`). `Game` has no `id` and no lifecycle/status field — see "single active game" below. `Game.leader` (current highest scorer, `null` before any round or on a tie) is distinct from `Game.winner` (`null` until someone actually reaches `targetScore`). `Game.orderedPlayers` returns `players` as-is or sorted by score depending on `sortMode` — presentation should always read player order through this, not `players` directly, when displaying (Settings' own reorder UI still edits/shows raw `players`, since that's the manual order itself). `Round.scoreForPlayer(id)` returns `null` (not a crash) if that round predates the player or they haven't scored yet — always prefer it over manually searching `playerRounds`.
  - `exceptions/`: one class per file, each `implements Exception` (e.g. `PlayerAlreadyInGameException`, `PlayerNotInGameException`, `InvalidPlayerNameException`, `InvalidPlayerOrderException`, `InvalidScoreException`, `RoundNotFoundException`, `NoPlayersInGameException`). Use cases throw these instead of a bare `Exception` so callers can pattern-match on type.
  - `use_cases/`: one class per business operation — `CreateGame`, `AddPlayer`, `RemovePlayer`, `RemoveAllPlayers`, `ReorderPlayers`, `RenamePlayer`, `CreateRound`, `RecordRoundScore`, `ResetGame`, `UpdateGameSettings`, `SaveGame`, `LoadGame`. Each exposes a single `execute(...)` method, is stateless, and returns a new immutable `Game` (via `copyWith`) rather than mutating in place. Use cases that touch persistence (`SaveGame`, `LoadGame`) take a `GameRepository` in their constructor; the rest take the `Game` to operate on as an argument.
    - `AddPlayer` backfills a `PlayerRound(score: null)` for the new player into every *existing* round — without this, a player added mid-game has no entry in earlier rounds and any code doing a raw lookup (instead of `Round.scoreForPlayer`) would crash.
    - `RemovePlayer` also strips that player's `PlayerRound` entries from every round (not just the top-level `players` list), so totals/leader don't leak scores from a removed player.
    - `RecordRoundScore` self-heals: if the round has no entry at all for that player (e.g. old data saved before `AddPlayer`'s backfill fix existed), it adds one instead of throwing.
  - `repositories/game_repository.dart`: abstract contract (`saveGame`, `loadGame`, `clearGame`).
- **`data/`** — implements the domain repository contract using Hive:
  - `models/`: `GameModel`, `PlayerModel`, `RoundModel`, `PlayerRoundModel` — Hive-serializable mirrors of the domain entities, each with `fromEntity()`/`toEntity()`. Enums (`GameMode`, `PlayerSortMode`) are stored as `String` via `.name` so the domain layer never depends on Hive, and so **enum declaration order can change freely** (it only affects UI iteration order, e.g. `AppThemeMode.values` in a `SegmentedButton`) without breaking persisted data.
  - **Hive `typeId` registry** (do not reuse or collide these when adding new Hive models, across *any* feature — it's one global namespace): `PlayerModel = 1`, `PlayerRoundModel = 2`, `RoundModel = 3`, `GameModel = 4`, `ThemePreferenceModel = 5` (in `settings`).
  - `datasources/game_local_data_source.dart`: `HiveGameLocalDataSource` reads/writes a single `GameModel` under a fixed key (`'current'`) in the `'active_game'` Hive box.
  - `repositories/game_repository_impl.dart`: converts between `GameModel` and `Game` and delegates to the data source.
  - `hive_registrar.dart`: `registerGameHiveAdapters()` — must be called once at app startup (in `main.dart`) before any Hive box is opened.
- **`presentation/`** — Riverpod (`flutter_riverpod`), no code generation:
  - `providers/game_providers.dart`: wires the repository and every use case into `Provider`s.
  - `providers/active_game_notifier.dart`: `ActiveGameNotifier extends AsyncNotifier<Game?>`. `build()` loads the persisted game (or `null` on first run). Every mutating method updates `state` and immediately persists via `SaveGame`.
  - `widgets/player_card.dart` (`PlayerCard`): one per player, rendered by `game_screen.dart`. Name and `totalScore/targetScore` sit in one row with a `PopupMenuButton` (⋮ "kebab" menu — Edit / Remove) at the end, all vertically centered as row siblings (don't reposition the menu with `Stack`/`Positioned`, it was tried and looked misaligned against the row text). The card's own background is a flat two-color `LinearGradient` cut at `totalScore/targetScore` progress (no fade — a soft fade was tried and looked broken at 100% progress since the fade zone landed past the "reached" point). Round score chips and the shared `widgets/tag.dart` (`Tag`) badge both intentionally use `colorScheme.primary`/`onPrimary` — the same colors as an *active* `CalculatorToggleTile` — as the app's one consistent "highlighted/active" visual language; keep new active-state UI consistent with that rather than reaching for `secondaryContainer`/`tertiaryContainer` (Material 3's chip/`SegmentedButton` defaults use those, which is why `Chip`s need `surfaceTintColor: Colors.transparent` and `SegmentedButton`s need explicit `style: SegmentedButton.styleFrom(selectedBackgroundColor: ..., selectedForegroundColor: ...)` overrides — otherwise they render a visibly different color from `primary`).
  - `screens/game_screen.dart`: the single screen of this feature — it *is* the game. There is intentionally no separate "create game" or "game list" screen, and no "add round" button: tapping a `PlayerCard` either fills in that player's pending score for the current round (creating a new round first if the previous one is fully scored) or edits their existing value. After a score is confirmed, if any *other* player in that same round still hasn't scored, the calculator reopens for them automatically (`_openCalculatorAndSave`'s loop) — it only returns to `game_screen` once the whole round is filled, or the user backs out without confirming. `PlayerRound.score` is `int?` — `null` means "hasn't played this round yet" (rendered as `?`), which is different from a real `0`. The AppBar also has a sort-order shortcut (same `PlayerSortMode` picker as Settings) so player order doesn't require leaving this screen.

### `calculator` feature

A full-screen calculator (`presentation/screens/calculator_screen.dart`) for computing a round's score, opened from `game_screen.dart` with the `Game.mode`, the player's name, and the round number. `domain/calculator_config.dart` defines, per `GameMode`, the number cards (each with a unique `id` so two cards can share the same `value`, e.g. Vengeance's double-13), the modifier cards (additive, `x2` multiplier, or `/2` divider — these only scale the *number cards* sum, never the additive modifiers or the Flip-7 bonus), and the Flip-7 bonus (7 *unique* card values selected). The layout is content in an `Expanded` above a full-width `FilledButton` pinned to the bottom (labeled `Confirm ($total)`, updates live) — a `SingleChildScrollView`-without-`Expanded` version was tried so the button would "hug" short content, but that's not what was wanted; keep the pinned-bottom layout. The AppBar has a reset action that clears all current selections/manual input. `presentation/widgets/calculator_toggle_tile.dart` (`CalculatorToggleTile`) is the reusable button widget for both grids — reused by the theme preview screen too.

### `settings` feature

- Game-level settings (mode, target score, player order, restart, add/remove/reorder/rename players) live in `presentation/screens/settings_screen.dart` and act directly on `activeGameProvider` from the `game` feature (cross-feature import is expected here). Player rename/remove are also available directly from each `PlayerCard`'s kebab menu on `game_screen.dart` — keep both in sync if the underlying use case's behavior changes.
- `settings_screen.dart` also has a "Rate on Play Store / Share app / Send feedback / Buy me a coffee" `Card` of `ListTile`s, backed by `url_launcher` (rate/support links, `mailto:` feedback) and `share_plus` (share sheet). Rate tries a `market://details?id=...` URI first (native Play Store app) and falls back to the `https://play.google.com/store/apps/details?id=...` web URL if that fails to launch — there's no iOS App Store branch, this action is Android-only by design. The feedback `mailto:` currently targets `echo.congrats636@passinbox.com`, a *different* alias than the Proton one used on the privacy policy page (see "App identity & store readiness" below) — confirm with the user whether that's intentional before consolidating either address.
- App theming: `domain/entities/theme_preference.dart` holds the pure-Dart `ThemePreference` (a `themeId` string + `AppThemeMode` enum: `light` / `system` / `dark`, in that declared order since `SegmentedButton` iterates `.values` directly) and is persisted via `ThemeRepository`/Hive, same pattern as `game`. **The actual color catalog lives in `presentation/theme/app_theme.dart`** (`AppTheme` class + the `availableAppThemes` list) — it depends on `Color`/`ColorScheme`, which is why it's in `presentation/`, not `domain/` (domain stays pure Dart). **To add a custom theme, add an entry to `availableAppThemes` in that file** — it picks up automatically in Settings > Theme (swatch, preview, persistence) with no other code changes. Most themes just pick a seed `Color` for `ColorScheme.fromSeed`; the `system` theme instead sets `buildColorScheme: _monochromeScheme` because `ColorScheme.fromSeed` can't produce true grayscale — even an achromatic seed like `Colors.grey` gets Material's default (blue-ish) fallback hue, so a genuinely monochrome theme needs its tonal colors specified by hand. `presentation/screens/theme_settings_screen.dart` shows the palette/brightness pickers *and* a live preview (real `PlayerCard` using the current game's leader if any, plus a few `CalculatorToggleTile`s) — keep the preview above the pickers, not below (tried both).
  - **Theme catalog, in order**: `system` (monochrome), `classic` (blue), `ocean` (blue-green), `forest` (green), `sand` (tan), `ruby` (red), `sapphire` (deep blue/indigo), `pearl` (pale warm ivory — deliberately *not* a pale blue/cyan, since that read too close to `ocean` once rendered through `ColorScheme.fromSeed`; a seed's hue matters far more than its lightness for how the generated scheme reads), `amethyst` (purple), `rose` (pink). The last five (Ruby/Sapphire/Pearl/Amethyst/Rose) are a deliberate nod to the Steven Universe Gems — keep that naming theme in mind if asked to add more to that set (e.g. a future gem-named color), rather than defaulting to nature words like the first few.

### Key product decisions (non-obvious from code alone)

- **No game history, no game "status"**: the app tracks exactly one active game at a time, like a persistent counter. There is no list of past games and no lifecycle state (no "finished" games) — `ResetGame` clears rounds but keeps the current players, and `mode`/`targetScore` can be changed at any time via `UpdateGameSettings`. Do not reintroduce a `GameStatus`/multi-game repository without confirming the requirement has changed.
- Reaching `targetScore` does not lock the game; `Game.hasPlayerReachedTargetScore` / `Game.winner` are purely informational getters used to highlight a leader in the UI. **There is currently no end-of-game celebration/notification at all** when a player reaches it — this has been flagged repeatedly as the single biggest missing feature but not yet built.
- New fields on a Hive model (`GameModel`, `ThemePreferenceModel`, etc.) must be added as **nullable** with a sensible default applied in `toEntity()`. Devices already have data persisted under the old schema; a non-nullable new field makes the generated adapter do `fields[n] as T` on missing data and crash with "type 'Null' is not a subtype of type 'T' in type cast" on load.

### App identity & store readiness

- **Bundle/package ID**: `com.eduardocortesherrera.flip7scoretracker` on both Android (`android/app/build.gradle.kts` → `applicationId`, plus `namespace` is deliberately left as the old `com.example.flip_7_score_tracker` — it's just Gradle's internal resource-generation namespace, doesn't need to match `applicationId`, and changing it would require moving `MainActivity.kt`'s package directory for no real benefit) and iOS (`PRODUCT_BUNDLE_IDENTIFIER` in `ios/Runner.xcodeproj/project.pbxproj`, all three build configs).
- **Display name**: "Flip 7 Score Tracker" (`android:label` in `AndroidManifest.xml`, `CFBundleDisplayName` in `Info.plist`). **Play Console developer name** (account-level, shown as "Developed by ___" on every app under this account) is the real name "Eduardo Cortes Herrera", not a pseudonym.
- **App icon**: a stack of 3 blank playing cards cascading diagonally toward the bottom-right (back → front: `#9E9E9E` → `#D6D6D6` → `#F5F5F5`), the frontmost card showing a bold dark "7", on a `#1E1E1E` background — same monochrome-with-one-accent language as the `system` theme. Source SVGs aren't kept in the repo (they were built ad hoc with a `sharp`/Node script in the scratch dir); only the two rendered 1024×1024 PNGs are: `assets/icon/icon.png` (full flat icon, used for iOS + Android fallback) and `assets/icon/icon_foreground.png` (the same design scaled to ~60% and recentered so it survives Android's adaptive-icon safe-zone circle — the flat `icon.png` composition is *not* safe-zone-safe on its own, don't reuse it directly as the adaptive foreground). Regenerate all platform sizes after changing either PNG with `dart run flutter_launcher_icons` (config lives in the `flutter_launcher_icons:` block at the bottom of `pubspec.yaml`, including `adaptive_icon_background: "#1E1E1E"`).
- **Release signing**: `android/app/build.gradle.kts` defines a `release` signing config that reads `android/key.properties` (keystore path/alias/passwords) if present, falling back to debug signing if it's missing (so a fresh checkout without the secret files still builds). **`android/key.properties` and `android/upload-keystore.jks` are real secrets, are git-ignored, and must never be committed** — they're backed up outside the repo. If they're ever missing on a machine that needs to cut a release build, that's expected; don't try to regenerate a new keystore casually, since a new one won't match what's already registered as the app's upload key in Play Console — ask the user first.
- **Privacy policy**: removed for now (was `docs/privacy-policy.html`, hosted via GitHub Pages from the `main` branch's `/docs` folder — that URL is dead until it's restored). The content still exists as a Word doc kept outside the repo, and this needs a new public home (a separate small public repo, another static host, etc. — the repo containing app source is meant to become private, and GitHub Pages on the free tier doesn't serve from a private repo) before Play Store submission can include a privacy policy URL again. The contact address used on it (and the Play Console developer-profile email) is a Proton "Hide-my-email" alias, not the user's real address — keep using that alias for anything else that's publicly displayed for this app; the user's real address is only used for the *private* Play Console account-recovery contact fields.

### Known gaps (deliberately not yet addressed)

- **No automated tests** — the project has been built iteratively without a `test/` directory. The domain `use_cases/` and `calculator_config.dart` (Flip-7/multiplier/divider math) are the highest-value candidates whenever this gets picked up.
- Monetization (premium themes via IAP, ads) has been discussed but intentionally not implemented yet.
- **Play Store submission is in progress** as of this writing (developer account created, identity verification pending) — the app itself, icon, and signing are done; the privacy policy needs a public URL again (see above) before the store listing can be finished, plus content rating, data-safety form, and a closed-testing track with 12+ testers for 14 days before production access.

### Toolchain gotcha

`hive_generator` pins `analyzer` to an older version (`6.4.1`) that cannot parse Dart's newer static-member shorthand syntax (e.g. `.fromSeed(...)`, `.center` without the enum/class prefix) that `flutter create` boilerplate sometimes uses. If `dart run build_runner build` fails with `SEVERE ... requires Dart inputs without syntax errors` pointing at an unrelated file, it's this — replace the shorthand with the fully-qualified form (`ColorScheme.fromSeed(...)`, `MainAxisAlignment.center`) rather than upgrading `analyzer` (that breaks `hive_generator`).
